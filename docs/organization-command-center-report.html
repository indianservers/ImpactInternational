Hierarchy service and security

GET /api/v1/structure/intelligence returns a genuinely nested tree, counts, search matches, geographic summaries, breadcrumbs and capability flags. Query filters: unitId, from, to, depth, search, refresh=1.

GET /api/v1/structure/intelligence/{id}/details reuses the original unit identity, officer appointments, permission-filtered governance requests and organization history. Leadership requires leadership.view; member aggregates require members.view; audit history requires audit.view. Governance results use the existing GovernanceService request query, including finance visibility rules.

Both endpoints enforce organization.view, the active workspace, tenant and visible subtree before returning data. Changing a URL ID cannot reveal a foreign unit. Club members retain their actual existing permission to see their own club's organization structure; member and leadership aggregates remain restricted.

The hierarchy is assembled exclusively from Org.ParentId and existing level IDs. No records, membership tables, leadership tables or schemas were duplicated. A second national branch with identical names was tested specifically to rule out name-based nesting.

Hierarchy snapshots use a bounded 32-entry, 20-second cache. Authentication, current permissions and visible IDs are checked before every cache lookup. Search does not reuse an unfiltered cached response. Refresh bypasses the cache; contextual saves refresh the current summary.

Definitions and practical limits

The main database remains at one organization, 625 clubs and 3,126 people. Test fixtures were created only in the separate QA/performance databases; their screenshots therefore show additional units.
  • Dates filter recorded unit creation and membership joins, using UTC day boundaries. Structure, membership status and office coverage are current records, not reconstructed historical snapshots. No historical organization structure is inferred.
  • Total members are distinct people, including qualifying affiliations joined by the selected end date. Active members additionally use current Active status and current expiry. A person in multiple clubs is deduplicated in parent totals.
  • Immediate children count only direct recorded children. Descendant clubs include the selected node itself when it is a Club. Active versus other status counts remain visible; archived records are preserved.
  • Creation comparisons use the selected and preceding equal-length periods. Join charts show observed joins rather than an invented retention series. Detailed historical retention remains in Membership Insights.
  • Mandatory office coverage counts active mandatory position definitions and currently effective Active appointments across the branch. Appointment details show original dates/statuses; successor management stays in the existing leadership workflow.
  • Event registrations are not attendance. The Activities tab uses the existing API and its maximum one-year range; unsupported longer ranges display its validation error.
  • Deep trees are bounded at 1,000 returned nodes and five loaded levels. Breadth-first loading preserves upper sibling branches; select a branch to load its deeper children. The tree renders only expanded loaded rows. More than 25,000 visible units requires narrowing the login workspace.
  • No coordinates or state boundaries were fabricated. Countries and recorded state summaries use existing club geography. State summaries are currently bounded to the top 20 states, and the displayed state count reflects that returned summary.
  • Twenty-second caching can briefly lag external changes; Refresh forces a new snapshot. Measurements are local observations, not production latency guarantees.
